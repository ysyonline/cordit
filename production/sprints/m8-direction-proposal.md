# M8 方向提案 · 切片收口之后往哪走

- **编制**：文策渊（design-strategist）｜**性质**：提案待拍板，不含实现；未做任何 git 操作
- **输入正本**：production/qa/m7-r3-recording-findings.md（三条缺口）、production/sprints/story-battle-item-persistence.md（已立 Story）、主理人 M8 待办池简报
- **工时换算口径**：用户每周 5-10h，参考 Sprint4 实际节奏（19h/3 周 ≈ 6.3h/周）；周数区间下限≈10h/周口径、上限≈5h/周口径

## 背景

M1-M7 七里程碑全部收口（tag m7，GUT 551/551，外部试玩「没有大问题」，代录 29 断言 PASS），30 分钟垂直切片处于"达标"状态。待办池现有五类素材：① design/ 目录丢失待恢复（git 4f3b717^ 可批量取回）；② 三条生产缺口——charge 蓄力无生产 UI 反应、战前对话 story_p3_boss_front 被转场强制收束（玩家实况同样看不到）、战斗内道具消耗不扣减（已立 Story P2）；③ o7 测试偶发超窗（CI 卫生）；④ 证据强口径（正式试玩问卷，仅对外发布需要）；⑤ 方向性空白（新内容 or 对外发布）。M8 的真实问题不是"做什么功能"，而是：**在"能玩"之上，下一个最值得 5-10h/周 的事情是什么**。

## 选项对比总表

| 选项 | 一句话定位 | 总工时 | 周数@5-10h/周 | 做完后的终态 | 核心风险 |
|---|---|---|---|---|---|
| A 打磨收尾 | 已知瑕疵清零，放心冻结 | 8-12h | ≈1-2.5 周 | 无已知瑕疵的冻结切片，随时可展示 | 最稳但止步，不产生新学习 |
| B 对外发布 | 切片见人，换回真实反馈 | 14-22h | ≈2-4 周 | itch.io 公开可玩 + 问卷反馈渠道 | Web 导出兼容性 |
| C 内容扩展 | 切片养成 40-50 分钟 demo | 20-31h | ≈2-6 周 | 走通"地图→遇敌→Boss→剧情"全内容管线 | 范围膨胀 + 孤岛迭代 |
| D 两段式（新提） | 先 A 后 fork，每小时零浪费 | 首段 8-12h | ≈1-2.5 周 + 决策点 | 干净地基 + 高质量 fork 决策 | 需防 fork 悬而不决 |

> 关键结构事实：**A 的全部工时是 B、C 的必修交集（共同前缀）**——缺口 b/c 不修，发布会被玩家踩、扩展会把经济失真放大；design/ 不恢复，内容设计没有依据正本。

## 选项 A · 打磨收尾向 ——「把切片做到无已知瑕疵，然后冻结」

- **工作项**（合计 8-12h）：
  1. design/ 恢复：批量 `git show 4f3b717^:design/<path>` 导出 + 按 sprint 文档引用核验路径完整（1h）
  2. 缺口 b 战前对话可见性：dialogue 动作加"等待收束"阻塞语义；**含 R-3 驱动器适配**（修复后对话将可见，录制链需处理推进）（2-3h）
  3. 缺口 c 道具持久化：按已立 Story 验收标准直做，消耗差分回写，与掉落正确叠加（2-3h）
  4. 缺口 a charge 横幅：**钉死最小口径**——charge 事件接入生产 UI 横幅；「返回数组→信号流」重构拆独立 Story 不进本方向（2-3h）
  5. o7 超窗放宽（0.5-1h）＋ 收口：GUT 全量回归 + 试玩确认 b 修复后的叙事节奏（1h）
- **代价与风险**：范围最小、风险最低。唯一膨胀点是 a 项重构诱惑，已钉死口径规避。
- **终态**：无已知瑕疵的冻结切片 + design 文档归位；项目处于"可随时展示、可随时续作"的干净休眠态。
- **机会成本**：不发布不扩展——学不到外部反馈这一课；若选纯 A 且不再 fork，项目实际进入休眠。

## 选项 B · 对外发布向 ——「让切片见人，用真实玩家换学习增量」

- **工作项**（合计 14-22h）：
  1. 必修子集：b、c 全修（对外玩家必踩）+ a 最小横幅（Boss 蓄力预告不可见 = 战斗不公平感）+ o7 + design/ 恢复带上（约 8-12h）
  2. **Web 导出 spike 前置**：Godot 4.7.2 网页导出 + 640×360 Nearest 缩放跨 DPI 验证 + 浏览器音频策略；spike 失败则降级 Windows 包 + 网盘分发（3-5h）
  3. itch.io 页面：说明文案、截图/GIF、tag（2-3h）
  4. 正式试玩问卷：证据口径从"代录断言"升级到"真实玩家结构化反馈"（1-2h）
- **代价与风险**：Web 导出兼容是最大不确定项（spike 前置可止损）；反馈量不可预期；首次对外曝光的心理成本真实存在。
- **终态**：公开可玩的 30 分钟切片 + 反馈渠道 + 作品集素材；第一次走完"发布"这一环。
- **机会成本**：无新内容；发布后运营与反馈处理会打断内容节奏；30 分钟体量对"demo"预期偏短。

## 选项 C · 内容扩展向 ——「把切片养成有推进感的 demo」

- **工作项**（合计 20-31h）：
  1. 硬前置：design/ 恢复（依据正本，恢复前不动内容笔）+ 缺口 b（事件执行器语义是新剧情链的公共路径，先修一次全链受益）+ 缺口 c（内容越多经济失真越放大）（6-9h）
  2. 新内容包，**钉死上限：1 张新地图 + 1 个新 Boss**（防 demo 无底洞）：
     - 新地图一层：克隆 town 生成→verify 管线（Sprint4 先例口径 3-5h）
     - 敌编组摆位 + 遭遇节奏（2-3h）
     - 新 Boss / 新战斗机制一个（3-5h）
     - 剧情文案一段（可回填 E7-S2 移出的弹性文案位）（2-3h）
     - 数值过三问测试 + GUT 覆盖（4-6h）
- **代价与风险**：学习价值最高的方向（完整走一遍内容生产管线），也是最容易膨胀的方向——上限条款必须执行；数值再平衡可能触碰 M7 已过口径；2-6 周无外部反馈的孤岛迭代。
- **终态**：40-50 分钟体量 demo；对"从 GDD 到可玩内容"全流程建立手感。
- **机会成本**：a 项不修，蓄力不可见带进更大体量；不发布则真实玩家检验继续推迟；方向偏差要到做完才发现。

## 选项 D · 两段式（本提案新提）——「先 A 后 fork，让每一小时都不白花」

- **结构**：第 1 段 = 方向 A 全部工项（8-12h）；第 2 段 = A 收口**当周**开 fork 决策——想验证市场/攒作品集 → B；想继续学内容管线 → C。
- **为什么敢提**：
  1. **共同前缀零浪费**：b/c/a-min/o7/design 恢复本来就是 B、C 的必修交集，A 的每一小时在两条路上全额复用；
  2. **fork 应在看清新状态后做**：b 修复后战前对话首次对玩家可见、道具经济开始真实扣减——这会改变 B 与 C 各自的真实工作量与优先级，修复前拍板是在看旧地图选路；
  3. 5-10h/周的节奏下，"两周后再决策"的延迟成本趋近于零。
- **代价与风险**：唯一风险是 fork 悬而不决——**钉死约束：A 收口当周必须拍板，不默认顺延**。
- **终态**：第 1 段同 A；决策时项目处于"无瑕疵 + 文档齐 + 状态清晰"的可审计基线。
- **机会成本**：比直接 B 晚约 2 周见人、比直接 C 晚约 2 周开工；但两者都被 A 必修项覆盖，净损失≈0。

## 推荐排序与理由

**排序：D > B > C > A**（纯 A 止步视同 D 未完成第 2 段）。

**如果是我，会选 D。** 三点理由：
1. 对第一次做游戏的人，下一个最大的学习增量几乎必然来自"真实玩家的真实反应"（B 的核心价值），而发布的品相底线由 A 决定——D 是通往 B 的最稳路径，同时给 C 留门；
2. 当前待办里，修复项与文档恢复是**硬债**，内容与发布是**选择债**——先还硬债再选，不用为选择焦虑；
3. 共同前缀结构意味着 D 在经济上严格不劣于直接 B 或直接 C。

何时跳过 D 直接选：有明确外部时点（活动/展示邀约）→ 直接 B，A 压缩到必修子集；确定近期不想见人、只想学内容管线 → 直接 C，但把 b/c/design 恢复排最前。
