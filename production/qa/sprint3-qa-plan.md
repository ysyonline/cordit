## 0. 文档定位与基线快照

### 0.1 这份文档是什么：把 QA 从"兼岗"升级为"独立门"

截至 M2，本项目的测试资产（SMK-01~12 + GUT 62 条）**全部是工程侧边写边测的产物**，性质是"开发者自测"：它回答"我写的东西能跑"，不回答"验收标准逐条可被第三方复现地验证"。

两者的差别不在多写几条用例，而在三件事：

| | 开发者自测（现状） | 独立 QA 门（本文档） |
|---|---|---|
| 用例来源 | 从实现反推（代码能做什么就测什么） | 从验收标准正推（GDD/EPIC 写了什么就必须验什么） |
| 红的解读 | "我刚改坏了，修一下" | "先判定是预期内红还是真回归，再决定修还是改造" |
| 放行人 | 写代码的人 | 不写代码的人给判定，用户拍板 |

Sprint 3 是切片最重 Epic（30h，纯函数 + 四指令 + UI 全套三面夹击）。一旦某个 Story 悄悄引入回归，最可能拖到 M3 收口才暴露——那时 6h UI 工时的沉没成本已经压在头上，砍序和返工都很难看。本文档的全部价值就是把暴露点从"M3 收口"提前到"每个 Story 开工前 5 分钟 + 完工后 20 分钟"。

## 1. 测试策略总纲

### 1.1 三层模型（测什么、在哪测、谁验、多久）

| 层 | 覆盖范围 | 承载方式 | 编写/执行 | 单次耗时 | 判绿标准 |
|---|---|---|---|---|---|
| **L1 纯函数层** | 队列生成与重算、击退、伤害/克制/浮动、中毒、逃跑判定 | GUT 全自动（`tests/gut/test_e3s2.gd` 等） | 程基岩写，严守真审断言覆盖 | **< 1 min** | 退出码 0 + 断言语义覆盖表（§1.5）逐项有对应用例 |
| **L2 场景层** | 指令状态机、信号链路、数据闭环（battle_finished / GameData 写回 / discovered_weakness_set） | GUT + headless 脚本（沿用 `tests/smoke/headless_*.tscn` 套路） | 程基岩写，严守真审 | **< 2 min** | 退出码 0 + 关键路径（遇敌→战斗→结算→回图）端到端跑通 |
| **L3 人眼层** | UI 布局（640×360 / 9-slice）、打击感、弹字与音效钩子、转场穿帮 | 30 分钟手工清单 + 试玩视频 #3 | 主理人/用户执行，严守真出清单与判定 | **20-30 min** | 清单逐条 PASS + 视频覆盖 §3.3 全部必录分镜 |

> **分层的唯一判据**：这件事"错了能不能被机器发现"。能 → L1/L2；不能 → L3。不要让 L3 的活儿假装自动化（截图对比在切片规模下是负收益），也不要让 L1 的活儿滑进 L3（"我看了一眼伤害数字好像对"不是验证）。

### 1.2 L1 首要契约：随机性必须外部化（本 Sprint 最关键的一条）

**问题**：GDD §3.6 伤害公式含"浮动(0.9~1.1)"，这是一项随机。若 `battle_logic.gd` 内部直接调 `randi()`/`randf()`，则：

- GUT 单测要么写成区间断言（区间断言**测不出"倍率算错了"这类真 bug**——×1.5 写成 ×1.4 仍然落在区间内）；
- 要么随机命中导致 flaky（E3-S2 的用例会每天随机红一次，CI 信号立刻被污染）。

**契约（建议写入 E3-S2 验收判据）**：

- [ ] `scripts/core/battle_logic.gd` 内部**零** `randi()` / `randf()` / `rand_range()` / `RandomNumberGenerator`
- [ ] 伤害/判定类函数的随机因子**由调用方以参数传入**（建议签名 `calc_damage(..., variance: float = 1.0)`），随机生成发生在场景层
- [ ] 队列生成（GDD §3.1）本身**不引入随机**——同输入同输出，可 `assert_eq` 整个数组

**验证方式（可自动化，30 秒内）**：

```
# 静态 grep 断言（E3-S2 完工判据）
grep -nE "randi|randf|rand_range|RandomNumberGenerator|randi_range" scripts/core/battle_logic.gd
# 预期：零命中
```

**收益**：同一函数既能跑确定性单测（variance 固定为 0.9 / 1.0 / 1.1 三个端点分别断言），又能跑生产（variance 随机）。这一个约定让 §3.6 全部数值公式可被硬断言，是后续 12h 数值平衡能"改 .tres 就生效、改完立刻知道有没有算错"的前提。

### 1.3 L1 断言选型纪律（防"假绿"）

| 被测对象 | 必须用 | 禁止 |
|---|---|---|
| 整数结果（HP/MP/伤害取整/队列长度） | `assert_eq` | 浮点裸 `==` |
| 浮点结果（倍率 ×1.5/×1.0/×0.5、逃跑概率） | `assert_almost_eq`（**显式写出容差**） | `assert_eq` 裸浮点 |
| 队列 / 顺序 / 集合 | 断言**整个数组相等** | 只断言长度或只断言首元素 |
| 状态机 / 可用性 | 断言 `disabled` 标志 + 可取消后的状态回退 | 只测"点了不崩" |

**反"只测不崩"条款**：每个 `func test_*` 至少含 1 条**语义断言**（断言值，不是断言存在性）。仅 `assert_not_null` / 仅实例化不报错的用例，评审判 **INCOMPLETE**，不计入覆盖。

### 1.4 各层"不测"清单（避免把 L3 的活儿塞进自动化）

- [x] L1/L2 不测：UI 元素的位置/尺寸/配色/9-slice 是否拉伸 → L3
- [x] L1/L2 不测：浮动数字动画时长、弹字出现的"手感"、音效是否响 → L3
- [x] L1/L2 不测：战斗背景截图模糊的视觉观感 → L3（只测"截图触发接口被调用"）
- [x] L3 不测：任何能用 `assert_eq` 判定的数值 → 一律下沉 L1

## 4. Bug 分级口径

### 4.1 严重度（Severity，描述"伤害多大"）

| 级别 | 定义 | 典型判据（本项目实例） |
|---|---|---|
| **Blocker** | 游戏不能继续 / 数据损坏 / 架构级倒退 | 崩溃；软锁（四指令全灰、状态机进去出不来、战斗永不结束）；`battle_logic.gd` 出现 `get_node`（违反 A1 铁律 3）；存档 schema 被破坏；主流程（遇敌→战斗→回图）断开；队列死循环 |
| **Critical** | 核心机制算错，或有合法路径走不通 | 验收标准原文不成立；克制倍率算错；击退跨轮；伤害公式写错；全灭不进失败流程；八要素缺一项；边缘 7 条任一条失败；数据表字段缺失/数值填错（E3-S1） |
| **Major** | 功能可用但明显偏离，有 workaround | UI 元素在场但位置明显错；某技能效果偏差但战斗可完成；数值偏差 >20% 且 GDD 有明文；逃跑成功率钳位失效但仅边界值错 |
| **Minor** | 不阻塞体验 | 文案错字；像素偏移 ≤2px；弹字时机差 0.2s；音效钩子未接但视觉正确；描述文本缺失 |

### 4.2 优先级（Priority，描述"多快修"）

| 级别 | 默认映射 | 含义 |
|---|---|---|
| **P0** | ← Blocker | 立即修，不得继续下一个 Story |
| **P1** | ← Critical | 本 Sprint 内修，阻塞当前 Story 通过 |
| **P2** | ← Major | 本 Sprint 内修；若主理人裁决挂账则转下 Sprint |
| **P3** | ← Minor | 一律挂账，打磨阶段统一处理 |

> 严重度与优先级可**解耦**：Minor 但改起来只要 2 分钟 → 当场修不必记账；Major 但触发路径玩家碰不到 → 主理人可裁 P3。解耦需要写明理由，不静默调。

### 4.3 阻塞矩阵

| 严重度 | 阻塞 Story 通过？ | 阻塞 M3 门？ |
|---|---|---|
| Blocker | ✅ 是（当场修，不得带病进入下一 Story） | ✅ 是（挂账数必须为 0） |
| Critical | ✅ 是（当 Story 内修完才许勾验收框） | ✅ 是（挂账数必须为 0） |
| Major | ⚠️ 阻塞"勾验收框"，但**主理人可裁决挂账**（需写明 workaround） | ⚠️ 挂账 **≤2 条**且每条有 workaround → 门判 CONCERNS 可过；>2 条 → FAIL |
| Minor | ❌ 否 | ❌ 否，一律挂账到 Sprint 4 / 打磨阶段 |
