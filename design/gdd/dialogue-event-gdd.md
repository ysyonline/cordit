# GDD：对话事件系统（14h）

> 作者：文策渊（design-strategist）｜阶段：系统设计｜汇编：游承峰（team-lead）
> 依据：概念文档定稿 + 架构 A5/A6/A7 + phase2-3 对齐报告两裁决
> 工程确认：程基岩已确认本 GDD 引发的 A7 接口变更（动作 10→9 种、dialogue id phase 映射、校验器三职责、原子写）

---

## 1. 概述与设计目标
- **定位**：承载支柱二"剧情在对话里"。全切片叙事的运行时底座：触发器（薄壳）+ 事件 JSON + 对话 JSON + DialogueRunner 状态机，与架构 A7 完全同构，本文档是 A7 的**设计侧展开**，不引入 A7 之外的新机制。
- **设计目标**：① 剧情写作（16h 的剧情片段）全程只改 JSON 不碰代码；② NPC 对剧情阶段"有记忆"，喂养玩家的对话狩猎行为；③ 状态机只有 4 态（IDLE→PLAYING→WAITING_CHOICE→PLAYING→IDLE），实现风险封顶。
- **不做什么**：不做对话图编辑器、本地化、flag 存储型分支（多结局已 Cut）、逐字语音、对话框内立绘动画（头像差分用静态贴图换帧）。选项分支"仅影响当句"（见 3.4）。

## 2. 玩家体验目标
- 对话逐字显示（30 字/秒），按键一次跳完整段、再按翻页——阅读节奏可控，不拖时间。
- 剧情阶段推进后回城找人聊天有新台词（6 个 NPC 有阶段增量，见 3.3）——"这个世界在回应我的进度"。
- 选择永远低风险：选项不影响任何持久状态，玩家敢选，不会选择前疯狂存档。

## 3. 系统机制详述

### 3.1 对话 JSON 完整字段规范（与 A7 示例严格一致）
文件：`data/json/dialogues/*.json`。一个文件 = 一段对话脚本，顶层为条目字典，入口固定为 `"start"`，条目间用 `next` 链接：

| 字段 | 类型 | 必填 | 规范 |
|---|---|---|---|
| `speaker` | string | 是 | 说话名；空串 `""` = 旁白/系统（无名字栏） |
| `portrait` | string | 否 | 头像差分 id（如 `kai_normal` / `kai_smile`）；缺省沿用上一条 |
| `text` | string | 是 | 单条 ≤ 60 汉字，超长由渲染层自动折行，**不设滚动历史**（Cut） |
| `next` | string \| `"END"` | 是 | 下一条目 id；`"END"` 结束对话并回 IDLE |
| `choices` | array | 否 | `[{"text": "...", "next": "..."}]`，仅可与 `next` 共存于同一条目；**数量上限 2** |

对话 JSON 完整示例（含选项与收束）：
```json
{ "dlg_inn_rina_p0": {
  "start": { "speaker": "莉娜", "portrait": "rina_smile",
    "text": "委托书写得密密麻麻的……喂凯尔，游击士都是这么过日子的吗？",
    "choices": [ {"text": "「大概吧。」", "next": "a1"},
                 {"text": "「你想回去了？」", "next": "a2"} ] },
  "a1": { "speaker": "莉娜", "portrait": "rina_normal", "text": "哦……那走吧。", "next": "END" },
  "a2": { "speaker": "莉娜", "portrait": "rina_angry", "text": "才、才没有！走吧！", "next": "END" }
}}
```
选项分支规则（3.4 详述）：两条分支尾巴 ≤2 条目且必须汇合到同一 `next`（示例中各自直接 END）。

### 3.2 事件 JSON 规范与动作类型最终清单（9 种，10 种内裁剪）
事件文件：`data/json/events/*.json`，格式与 A7 示例一致（`event_id / conditions / actions`）。

**动作类型最终确认 9 种**——对 A7 的 10 种做一处替换：
- **裁掉 `check_flag`**：其职能已被事件级 `conditions`（`story_phase` / `not_flag`）完全覆盖；选项分支"仅影响当句"不落 flag，运行时无需条件跳转。保留它=鼓励做 flag 分支，与 Cut 清单相悖。
- **新增 `set_story_phase`**：剧情阶段推进是 Must 机制（NPC 刷新与事件条件都消费它），必须可由事件触发。总数仍封顶 10 内（9 种）。

最终清单与用途映射：
| 动作 | 用途 | 频次预估 |
|---|---|---|
| `dialogue` | 播放对话脚本 | 全部事件 |
| `give_item` | 宝箱/掉落/剧情给道具 | ~15 |
| `set_flag` | 宝箱开启、一次性事件标记 | ~15 |
| `battle` | 触发战斗（Boss 战前后事件用） | 1 |
| `heal` | 客栈休息全回复 | 1-2 |
| `teleport` | 地图切换（探索 GDD 4.4） | ~12 |
| `save_point` | 客栈存档点 | 1 |
| `set_story_phase` | 剧情阶段推进（3 个切换点） | 3 |
| `wait` / `play_sfx` | 事件节奏停顿 / 音效钩子（Should-have 音效落地时启用） | 少量 |

`conditions` 字段仅 3 种键：`story_phase: [运算符, n]`、`flag: "x"`、`not_flag: "x"`——不扩展。

**工程侧实现约定（程基岩确认）**：
- phase 映射选取规则：取 **≤ 当前 story_phase 的最大键**（keys{0,1} 且 phase=2 时选 "1"）；键必须是字符串数字，解析器加载期规范化为 int，至少含一个 "0" 兜底键，非数字键报错。
- 加载期校验器三大职责：① 动作 type 白名单（9 种，未知 type 报错）；② 引用完整性（dialogue id / next / choices.next / battle 的 enemy_group_id / give_item 的 item_id 全部必须可解析到实际文件）；③ 结构校验（必填字段、conditions 键只允许三种）。

### 3.3 剧情阶段（story_phase）机制
- **阶段定义**（GameData 中单 int，EventBus 广播 `story_phase_changed(n)`）：
  - **Phase 0 日常**：开场→接受委托前。小镇全貌呈现，NPC 日常对话。
  - **Phase 1 事件**：接受委托→抵达遗迹前。异变发生，道路解锁，NPC 议论。
  - **Phase 2 调查**：进入遗迹一层（触发确认事件）→Boss 战前。
  - **Phase 3 收束**：Boss 战后事件→钩子结尾（切片终态）。
- **切换触发点（全项目仅 3 处，均为事件动作）**：
  1. `0→1`：委托所室内事件 `story_quest_accept` 的末尾动作。
  2. `1→2`：遗迹一层入口事件 `story_ruin_enter` 的末尾动作。
  3. `2→3`：Boss 战事件 `story_boss_pre` 战后段内（见探索 GDD 接口回签 I5）。
- **NPC 阶段对话刷新规则**：NPC 节点只带 `npc_id`；其交互事件运行时按 phase 从映射选对话 id：
```json
{ "event_id": "npc_innkeeper", "conditions": {},
  "actions": [ {"type":"dialogue","id":{"0":"dlg_innkeeper_p0","1":"dlg_innkeeper_p12"}} ] }
```
（dialogue 动作的 id 允许"phase→脚本"映射形态，`"1"` 表示 phase≥1 沿用。）
- **阶段对话配额（Must）**：小镇 12 名 NPC 中，**6 名必须有 Phase 1/2 增量对话**：委托所前台菲奥拉、客栈老板、广场小孩、武器店老头、镇口守卫、神秘旅行者（钩子铺垫位）。其余 6 名单阶段对话即可。

### 3.4 选项分支"仅影响当句"的落地规则
1. 选项只允许出现在对话条目上，每处 ≤2 个选项。
2. 分支尾巴 ≤2 条目，且两条尾巴必须在 ≤2 步内汇合到同一 `next`（或各自 END）。
3. 分支内**禁止** `set_flag` / `set_story_phase` / `give_item`——选项无持久后果，schema 校验器直接拒绝（工程侧义务，已确认）。
4. 选项的价值定位：塑造角色（玩家替主角"选语气"），不制造叙事差。

### 3.5 剧情片段（16h）的文本预算与文件组织
**文本预算（总 330 条，预算上限 350）**：
| 块 | 内容 | 条数 |
|---|---|---|
| 主线四拍 | P0 开场+委托(50) / P1 异变+出发(55) / P2 遗迹推进(55) / Boss前后+钩子(50) | 210 |
| NPC 阶段刷新 | 12×日常(~24) + 6×增量(~18) | 42 |
| 队员聊天 | 2 段 × 18 条（P1 道路 1 段、P2 遗迹二层 1 段） | 36 |
| 调查/宝箱文案 | 18 调查点 + 9 宝箱 | 27 |
| 选项尾巴 | ~15 条目 | 15 |

**文件组织约定**：`dialogues/story/p0_intro.json…p3_finale.json`（主线按拍分文件）/ `dialogues/npc/npc_<id>.json`（含各阶段条目）/ `dialogues/map_<map>_flavor.json`；`events/story/*.json`（剧情锚点）/ `events/map_<map>.json`（该图全部宝箱/调查/传送/NPC 事件）。写作顺序 = Phase 顺序，每拍写完即进游戏跑一遍（JSON 热改不改码，正是 A7 的兑现）。

## 4. UI/呈现需求
对话框要素（对接 UI 布局规格，视口 640×360）：名字栏 + 头像窗（左侧，差分切换）+ 文本区（≤2 行半，自动折行）+ 继续箭头（翻页可按提示）+ 选项列表（最多 2 项，光标选择）。逐字 30 字/秒；按键 1 = 补完本条，按键 2 = 翻页/确认选项。对话期间玩家移动锁定（A7）、其他触发器不响应。

## 5. 数据结构需求（战斗 GDD 之外新增字段）
- 对话 JSON / 事件 JSON（上文 3.1/3.2 规范即 schema，校验器逐字段校验 + 引用完整性）。
- GameData 新增：`story_phase: int`、`flags: [string]`。存档 schema（ADR-3）对应追加此二字段（工程已确认无冲突）。

## 6. 与其他系统的接口
- **I3 消费方**：`set_flag`/`story_phase` 写入 GameData → 进存档。
- **I5 提供方**：Boss 战前后事件锚点（回签详述，见探索 GDD 第三部分）。
- **对战斗**：`battle` 动作把事件流暂停交给战斗，胜利后恢复执行（逃跑对 Boss 禁用；剧情事件中不放可逃战斗）。
- **对探索**：交互触发器/踩踏触发器是本系统的入口。

## 7. 边缘情况（5 条）
1. JSON 引用悬空（next 指向不存在条目）：加载期校验拦截，游戏内不出现。
2. 对话期间踩到传送点：对话锁移动且触发器休眠，不可能发生；若因存档读档重叠出现，触发器在对话状态机非 IDLE 时一律忽略。
3. 同格多触发器（调查点+传送点相邻）：优先级 交互键触发 > 踩踏触发；同类型按触发器面积重叠时取最近创建序（制作规范：禁止故意重叠摆放）。
4. 选项界面时玩家按了取消/移动键：忽略，必须显式选择一项（每处选项必选其一）。
5. 存档在对话中途读入（失败读档等）：读档后状态机强制回 IDLE。
